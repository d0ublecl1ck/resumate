# 用户故事：求职者

> 来源：《Resumate：对话式简历编辑系统》产品文档。索引见 `README.md`。
> 优先级：P0 = MVP 必须；P1 = 迭代增强；EXT = 比赛扩展。
> 格式：作为【角色】，我希望【目标】，以便【价值】。

---


## Epic 1：简历管理（多简历 CRUD）

### US-1.1 对话创建简历【P0】
作为求职者，我希望在对话中说"创建一份后端工程师简历"，以便 Agent 自动为我创建简历草稿并引导我补齐内容。
- [ ] Agent 调用 `create_resume` 创建草稿并返回新简历
- [ ] 通过多轮对话补齐个人信息与工程内容
- [ ] 创建过程实时生成结构化简历与预览


### US-1.2 简历列表管理【P0】
作为求职者，我希望在简历列表中新建、复制、重命名、归档、删除、搜索和排序简历，以便并行管理多份针对不同岗位的简历。
- [ ] 列表支持新建、AI 创建、复制、重命名、归档、删除
- [ ] 支持搜索、排序、标签与最近编辑筛选
- [ ] 删除为软删除，支持恢复窗口


### US-1.3 复制简历创建岗位分支【P0】
作为求职者，我希望复制现有简历创建岗位定制分支，以便在保留原版的基础上针对不同 JD 微调。
- [ ] `POST /api/resumes/:id/duplicate` 生成完整副本
- [ ] 副本可独立编辑，不影响原简历


### US-1.4 对话切换当前简历【P0】
作为求职者，我希望在对话中引用或切换简历，以便 Agent 明确知道我当前编辑的是哪一份。
- [ ] 对话上下文绑定明确的 `active_resume_id`
- [ ] 切换后 Agent 后续操作均作用于新简历


### US-1.5 手动结构化编辑【P0】
作为求职者，我希望在中间编辑器直接修改简历字段，以便对 Agent 产出做精细调整。
- [ ] 手动编辑与 Agent 编辑走同一 Patch/Version 语义
- [ ] 编辑结果实时反映到右侧预览

## Epic 2：对话式编辑（Agent 核心交互）

### US-2.1 自然语言编辑简历【P0】
作为求职者，我希望说"把项目经历第二条改得更量化"，以便 Agent 将意图转为结构化 Patch 并展示 Diff。
- [ ] Agent 先 `get_resume` 获取当前版本与 `current_version_id`
- [ ] 自然语言意图转为结构化 Patch（稳定 section_id/item_id 级精确修改）
- [ ] 前端展示 Diff，用户确认后才 `apply_patch`


### US-2.2 跨简历语义操作【P0】
作为求职者，我希望说"基于这份简历创建 Java 岗版本""比较校招版和社招版"，以便用自然语言完成跨简历操作。
- [ ] 支持创建岗位版本、语义比较、批量引用的对话指令


### US-2.3 对话式撤销与回滚【P0】
作为求职者，我希望说"撤销刚才修改""回到昨天版本"，以便用自然语言完成版本操作。
- [ ] 支持 undo/redo 与指定版本 restore 的对话指令
- [ ] 回滚前展示反向 Diff 预览


### US-2.4 流式对话体验【P0】
作为求职者，我希望看到流式文本输出、工具执行进度，并能取消和重试，以便掌控 Agent 执行过程。
- [ ] SSE 流式输出与工具进度事件
- [ ] 支持取消当前 Run 与失败重试


### US-2.5 多对话恢复【P1】
作为求职者，我希望恢复历史对话并继续编辑，以便跨会话持续完善简历。
- [ ] 多对话列表与恢复
- [ ] 长对话上下文压缩，不丢失当前简历状态

## Epic 3：Diff 审阅

### US-3.1 类 Git Diff 审阅【P0】
作为求职者，我希望在任何修改提交前看到类 Git 的 Diff（新增绿、删除红、行级对照），以便准确判断 Agent 改了什么。
- [ ] 章节与字段级 Diff，可展开上下文
- [ ] preview 返回 before、after、unified diff 与语义摘要
- [ ] Agent 永远先 propose，不直接改当前版本


### US-3.2 逐项审阅控制【P0】
作为求职者，我希望逐项接受、拒绝、编辑后接受或全部接受，以便细粒度控制每次提交内容。
- [ ] 支持单项/全部接受、拒绝、编辑后接受
- [ ] 显示 Agent 修改理由与提交说明
- [ ] 同一 Patch 不能重复提交

## Epic 4：版本管理

### US-4.1 不可变版本与历史【P0】
作为求职者，我希望每次提交生成不可变版本并查看提交时间线，以便追溯每次变更。
- [ ] 每次提交原子生成 ResumeVersion 并推进 `current_version_id`
- [ ] 时间线展示提交时间、作者、消息和变更摘要
- [ ] 版本记录 actor、source、agent_run_id、user_turn_id


### US-4.2 版本对比【P0】
作为求职者，我希望对比任意两个版本，以便了解两次修改之间的差异。
- [ ] `GET /api/resumes/:id/diff?from=&to=` 支持任意两版本对比


### US-4.3 回滚与恢复【P0】
作为求职者，我希望回滚到历史版本并能撤销/重做，以便放心尝试修改。
- [ ] restore 生成新版本而非改写历史
- [ ] 支持 undo/redo
- [ ] 回滚前预览反向 Diff


### US-4.4 版本来源识别【P0】
作为求职者，我希望每个版本清晰标记"手动编辑"或"Agent 编辑"及其触发消息，以便审计变更来源。
- [ ] 版本携带 source、execution_mode、actor、触发消息关联
- [ ] Agent 版本可关联完整工具调用链

## Epic 7：Profile 工程（个人事实档案）

### US-7.1 建立个人事实总档案【P0】
作为求职者，我希望维护一份不受一页纸限制的完整职业档案（经历、项目、技能、教育、证据），以便作为所有简历的事实源。
- [ ] Profile 与 ProfileFact CRUD（type、tags、source、evidence、confidence、visibility）
- [ ] 时间线、经历、项目、技能与证据库视图
- [ ] 标签、搜索、筛选和事实验证状态


### US-7.2 基本信息一次维护、处处复用【P0】
作为求职者，我希望把姓名、年龄、联系方式等长期不变的信息只维护一份在资料中，以便创建任何简历时自动带出，无需重复填写。
- [ ] 基本信息集中在 Profile 统一维护
- [ ] 新建简历（手动或 Agent 创建）默认引用 Profile 基本信息
- [ ] Profile 基本信息更新后，新建简历自动使用最新值
- [ ] 已存在简历可显式同步并预览 Diff，不被静默改动


### US-7.3 Profile 版本管理【P0】
作为求职者，我希望 Profile 也有 Diff、版本历史与回滚，以便安全管理个人事实。
- [ ] ProfileVersion 不可变快照与版本 API
- [ ] Profile Diff 与 restore


### US-7.4 岗位匹配检索【P0】
作为求职者，我希望根据目标岗位 JD 检索 Profile 中相关事实，以便快速定位可用素材。
- [ ] `match-job` 返回相关事实、证据、置信度与匹配理由
- [ ] search 支持 query、target_role、filters、limit


### US-7.5 Profile 反向引用【P0】
作为求职者，我希望看到每条事实"用于哪些简历"，以便评估修改影响。
- [ ] 事实级反向引用列表
- [ ] 删除事实前展示受影响 Resume

## Epic 8：Profile 驱动生成简历

### US-8.1 从 Profile 生成岗位简历【P0】
作为求职者，我希望输入目标岗位 JD，让 Agent 从 Profile 挑选相关事实生成简历草稿，以便快速产出针对性简历。
- [ ] Agent 检索相关事实并说明选择理由，用户确认后创建 Resume
- [ ] 必要时 Agent 追问缺失事实
- [ ] AI 只抽取目标岗位相关内容，不复制全部 Profile
- [ ] 基本信息（姓名、年龄、联系方式等）自动带出，无需用户重复填写


### US-8.2 跨方向复用 Profile【P0】
作为求职者，我希望同一 Profile 生成爬虫、AI、全栈等不同方向简历，以便一次维护多处复用。
- [ ] 每份 Resume 记录 target_role、job_description 与 profile_version_id
- [ ] 可追溯每段简历内容来自哪个 ProfileFact 与版本


### US-8.3 Profile 与 Resume 边界【P0】
作为求职者，我希望 Profile 更新不会静默改动已生成简历，以便已投递简历保持稳定。
- [ ] Resume 保存选中事实的快照或引用与生成文案
- [ ] 同步需用户显式触发并预览 Diff


### US-8.4 简历事实晋升回 Profile【P0】
作为求职者，我希望简历中新增的事实经我确认后才写入 Profile，以便事实源不被污染。
- [ ] 新事实默认只存在于 Resume 草稿
- [ ] `promote_resume_fact_to_profile` 需用户确认

作为求职者，我希望内置 Agent 以可控轮次执行任务（限制轮次、Token、成本、超时），以便执行过程可预期、可取消。

- [ ] 只读工具自动调用；创建简历按用户意图自动执行
- [ ] 内容写入、删除、回滚、覆盖导出需确认
- [ ] 确认对象绑定 tool_call_id、resume_id、base_version_id

## Epic 10：执行模式（授权 / Full Access）

### US-10.1 授权模式【P0】
作为求职者，我希望默认模式下每次写入前都生成 Diff 并等待我确认，以便完全掌控修改。
- [ ] 只读操作自由执行，写入前 PendingAction + Diff 确认
- [ ] 删除、回滚、覆盖导出等高影响操作单独授权


### US-10.2 Full Access 模式【P0】
作为求职者，我希望开启 Full Access 后 Agent 无需逐次确认即可连续修改，以便高效完成大批量编辑。
- [ ] 写工具直接执行，一个用户消息轮次结束后自动提交聚合版本
- [ ] 前端展示执行进度、最终 Diff 和一键撤销
- [ ] 用户可随时停止、撤销、回滚或关闭 Full Access


### US-10.3 模式作用域与固化【P0】
作为求职者，我希望模式可配置为系统默认、单次会话或单个 Agent 级别，且运行中不被隐式切换，以便行为可预期。
- [ ] 每个 AgentRun 启动时固化 execution_mode
- [ ] 模式只影响授权门，不改变版本、审计和并发规则
- [ ] Full Access 开启/关闭记录审计事件；所有写入仍走 Patch 与 Version Service

## Epic 11：版本聚合（UserTurn 与手动缓冲）

### US-11.1 Agent 轮次聚合版本【P0】
作为求职者，我希望一条消息触发的多次 Agent 修改只产生一个版本，以便版本历史干净可读。
- [ ] 同一 UserTurn 内中间 Patch 写入 Working Copy，finalize 时聚合为一个版本
- [ ] 无实际变化的轮次不创建空版本
- [ ] 一轮涉及多份简历时，每份分别生成一个版本


### US-11.3 手动编辑防抖合并【P0】
作为求职者，我希望连续手动编辑（间隔 <30 秒）只生成一个版本，以便避免版本历史爆炸。
- [ ] 30 秒静默计时器，每次新修改刷新；超时自动提交 source=manual 聚合版本
- [ ] 切换简历、离开页面、显式保存或导出时立即 flush
- [ ] 不同 Resume 的合并窗口相互独立

## Epic 12：开放生态

### US-12.2 细粒度授权 Token【P0】
作为求职者，我希望按 scope（profile:read、resume:write 等）发放 Token 并限制资源与有效期，以便最小化授权面。
- [ ] PAT 按 profile/resume × read/write 授权，可限定具体资源 ID 与有效期
- [ ] 用户可随时撤销 Token 并查看访问日志
- [ ] 外部 Agent 写操作仍经过 Diff、权限与版本层，语义与内置完全一致


### US-12.3 数据可移植性【P0】
作为求职者，我希望导出 Profile、Resume 与全部版本历史为开放格式，以便随时迁移到其他系统。
- [ ] Profile 与 Resume 支持 JSON/Markdown 导入导出
- [ ] 不使用私有格式；外部 Agent 创建的版本标记 client_id，不降级为二等数据
