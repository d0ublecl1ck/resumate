# S2 解决方案

> 参赛队：RMD　赛题：A11《AI 模拟面试与能力提升软件》
> 组别：本科生组（应用类）　命题企业：锐捷网络

## S2A 目标与服务模型

**负责人：队长（产品与开发）**

### S2A.1 目标

让求职者的面试练习从「一问一答」变为「有据可查的训练」：题目来自目标岗位，追问来自本人简历，评分引用原话，薄弱项直接转为下一步练习。

对应赛题 A11 的四项任务，本方案给出四级服务模型：

| 级 | 服务 | 用户可见产出 |
| --- | --- | --- |
| 1 | 岗位化题库与知识库 | 按岗位与题型组织的题目、参考答案、知识依据 |
| 2 | 多模态多轮面试 | 一次可暂停、可回看的模拟面试会话 |
| 3 | 多维分析 | 分维度的评估报告，逐条附证据 |
| 4 | 能力提升反馈 | 练习计划、复测入口、成长曲线 |

### S2A.2 服务边界与可信性设计

本方案与通用 AI 面试工具最核心的差别，是 AI 能直接操作主档、简历、岗位、面试、练习五类实体，且全部落到可检验的产品约束：

1. 回答必须有依据。知识库检索无命中时，明确标注「依据不足」，禁止编造知识库引用（对应 US-14.2）。
2. 不可测的指标不虚构。纯文本场次不产生音频信号，语速与清晰度一律标为「不适用」；自信度标注为「有依据的估计」，而非事实诊断（对应 US-14.4）。
3. 口径不可比就不比。不同岗位或不同量表版本的成绩不连成同一条成长曲线，只并列展示（对应 US-14.5）。
4. 全链路可追溯。每次评估结论可回指到具体的一轮问答、具体的量表版本与具体的知识条目。

### S2A.3 服务对象与场景

面向计算机相关专业、准备技术岗面试的在校学生与应届求职者。典型场景：选定目标岗位与简历 → 完成一轮 20–30 分钟模拟面试 → 阅读评估报告 → 按计划练习 → 复测并对比成长曲线。

### S2A.4 系统能力的组织方式

本项目把简历事实、多版本简历、岗位需求结构化并版本化，面试与评估能力构建在同一套架构之上，能力组织方式见 S2C.4。

## S2B 组织管理与业务分析方案

**负责人：队长（产品与开发）**

### S2B.1 团队角色与职责

团队以服务外包开发规范组织，三种角色贯穿全周期：

| 角色 | 主要职责 | 关键交付物 |
| --- | --- | --- |
| 队长（产品与开发） | 产品定义与需求拆分、界面与交互、核心功能开发、里程碑与验收组织、成本模型与可行性分析复核 | PRD 与屏幕流定义、核心功能代码、里程碑与验收记录 |
| 开发 | 部分功能开发、接口对接与联调、模块级自测、成本模型与可行性分析 | 接口契约与联调记录、模块代码、模块自测记录、成本模型与可行性分析 |
| 测试 | 测试设计与用例、缺陷复现与回归、端到端走查与质量门禁执行 | 测试用例与缺陷记录、门禁与端到端报告 |

三种角色均在同一仓库协作，全部需求、变更与验收以仓库内的 Issue 与文档流转，形成可核查的过程记录。

### S2B.2 过程管理

采用看板式迭代，每个迭代固定四步：需求登记 → 设计与接口冻结 → 实现与自测 → 评审与验收。每个变更都有唯一编号，从需求、实现到验收可逐条追溯；未关联编号的代码变更不予合入。

### S2B.3 质量门禁

仓库已建立自动化质量门禁并在提交前强制运行，`quality-gates/gates/` 下共 5 个门禁脚本，本方案统一执行且不放宽：

1. Issue 文档门禁（`generic-project.js`）：需求、变更与验收以 Issue 文档登记，字段或状态不一致即失败。
2. 界面国际化门禁（`ui-i18n.js`）：用户可见文案必须经翻译键渲染，中英词条结构一致，禁止硬编码中文字面量。
3. 表单与错误契约门禁（`ui-form-contract.js`）：命名表单必须接入 schema 校验，错误码必须映射为文案，禁止直接透出后端报错原文。
4. 隐私门禁（`repo-privacy.js`）：Git 跟踪文本不得出现本机路径、个人邮箱与内网地址。
5. 含糊实现检查（`no-fake-implementation.js`）：含糊实现必须写成结构化 `TODO(fake)` 标记，便于统一检索。

### S2B.4 业务分析

痛点侧：高校学生面试练习依赖同学互问或公开题库，题目与简历脱节、反馈主观且不落证据。通用 AI 工具能生成问题，但缺少岗位知识约束与评估证据链。

对策侧，本方案把「岗位题库 + 简历事实 + 量表 + 证据链」四件东西绑在一起，使评估结论可解释、可复核，这既是产品价值，也是评委可验证的交付点。

### S2B.5 交付物清单

| 阶段 | 交付物 |
| --- | --- |
| 设计 | 需求与边界说明、接口契约、数据模型与量表定义 |
| 开发 | 后端面试与评估模块、前端面试与报告界面、按岗位分片的题库与知识库数据 |
| 验证 | 单元与接口测试、评分一致性抽检样本、端到端演示脚本 |
| 交付 | 可运行系统与部署说明、用户使用说明、演示材料 |

## S2C 技术路线及实现方案

**负责人：队长（产品与开发）与开发共同**

### S2C.1 总体架构

统一采用同一套前后端分层：React 前端经 HTTP 调用 FastAPI 后端，后端按领域模块分层；模型调用由独立的 Agent 运行体进程完成，经公共接口与后端交互，不直接访问数据库。

面试链路（同一系统内已交付）：

1. 前端发起「开始面试」请求，后端创建面试会话并冻结上下文快照（简历版本 + 岗位需求 + 题库岗位）。
2. 后端组装题目，从岗位知识库做词法检索（BM25）取依据，交给模型生成题目与参考要点。
3. 用户以文字或语音作答；语音先转写并回显供本人核对。
4. 面试官按回答要点与岗位要求决定追问或进入下一题。
5. 会话结束后按冻结量表逐维度评分，逐条绑定证据（原话片段 + 知识条目）。
6. 生成报告与练习计划，写入成长记录，供曲线对比。

### S2C.2 对应 A11 四项任务的技术方案

**（1）岗位化题库与知识库**

- 岗位维度可扩展：题库与知识库都按 role 组织——知识文档 `KbDocument.role`（`backend/app/modules/kb/models.py:20`）、题目 `BankQuestion.role`（`backend/app/modules/bank/models.py:21`，带索引与 (role, prompt_hash) 唯一约束）；中文/英文语料按岗位分片（`backend/app/modules/kb/corpus/java-backend/` 23 篇、`web-frontend/` 12 篇）。
- 检索与引用回填都限定在同一 role 作用域：`GET /kb/documents?role=`、`GET /kb/search?q=&role=` 与题目查询均按 role 取数；`backend/app/modules/kb/backfill.py` 用 `service.search(..., role=question.role)` 回填引用，形成同一岗位内的依据链，不跨岗位串味。
- 检索机制：词法检索（BM25 打分，含 IDF 与标题字段加权），命中片段作为「知识依据」注入出题提示词，出题后再按题干检索把出处落到引用字段；无命中即标注「依据不足」，不返回编造内容。
- 当前两个目标岗位（Java 后端、Web 前端）为验证样本（赛题要求至少两种）；新增岗位 = 加语料目录 → 导入为带 role 的文档 → 生成或录入带同一 role 的题目 → 按 role 回填引用，无需改架构。
- 本地知识库资料随作品提交（`本地知识库资料.zip`，含两个岗位分片语料与索引说明），对应命题【提交材料】第 (5) 项。
- 题目与简历绑定：项目深挖类题由简历中的具体项目生成，面试中可回指简历条目。

**（2）多模态交互界面**

- 文字与语音双通道，同一会话内可混用。
- 语音链路拆为转写与播报两段，各自独立失败；任一不可用即降级为纯文字，并保留已有对话上下文。
- 多轮对话与智能追问：会话状态由后端持有，前端只渲染；追问依据来自当前回答要点缺失项与岗位要求。
- 幂等：同一作答重复提交只记录一次，避免重复计分。

**（3）多维度分析模块**

内容维度：技术正确性、知识深度、逻辑严谨性、岗位匹配度。
表达维度：语速、清晰度、自信度（语音场次）；纯文本场次前两项标「不适用」。

评分约束：量表版本冻结并随报告存储；每个维度必须给出证据片段；证据不足时该维度标为「证据不足」而不给分。同一份回答在不同量表版本下不参与同一趋势对比。

**（4）能力提升反馈**

- 薄弱维度映射到练习项，每项含目标、练习材料与复测入口。
- 成长曲线按「同岗位 + 同量表版本」聚合，口径不一致时并列展示。
- 练习与复测结果回写同一成长记录，形成闭环。

**（5）AI 可操作实体与工具清单**

AI 对主档、简历、岗位、面试、练习五类实体都有读写路径，写操作一律经待确认与审批。可操作范围与工具如下：

- Agent 工具集（`agent-core/src/resumate_agent_core/tools.py`）：`capability`、`create_turn`、`get_turn`、`finalize_turn`、`cancel_turn`、`validate_patch`、`preview_patch`、`apply_patch`、`list_pending_actions`、`get_working_document`。
- 审批与补丁（`backend/app/modules/agent/api.py`）：`POST /pending-actions/{action_id}/approve`、`POST /pending-actions/{action_id}/reject`；`POST /turns/{turn_id}/patches:validate`、`POST /turns/{turn_id}/patches:preview`、`POST /turns/{turn_id}/patches:apply`。
- 岗位实体（`backend/app/modules/jd/api.py`）：`POST /jds:parse-image`、`POST /jds:parse-text`、`PUT /jds/{jd_id}/binding`；微调入口创建绑定该 JD 的 Agent run。
- 面试实体（`backend/app/modules/interview/api.py`）：`POST /interview/sessions`、`POST /interview/sessions/{session_id}/answers`、`POST /interview/sessions/{session_id}/finish`、`POST /interview/sessions/{session_id}/regenerate`；练习：`POST /interview/practice-items`、`PATCH /interview/practice-items/{item_id}`。

### S2C.3 数据模型（同一系统内交付）

新增面试会话、面试轮次（题目与作答、含转写文本与音频可用性标记）、评分记录（量表版本 + 各维度得分 + 证据引用）、练习计划与练习项、成长记录。所有新增表统一采用同一套迁移机制管理，不修改其余表的语义。

### S2C.4 同系统能力的分工与共用

| 同系统能力 | 面试链路如何共用 |
| --- | --- |
| 角色权限与访问控制 | 面试会话与报告共用一个身份与权限判定，报告默认仅本人可见 |
| 访问审计 | 面试与评估关键操作写入同一套审计通道 |
| 多模型接口与密钥托管 | 共用同一模型配置与加密托管机制，不引入厂商专有 SDK |
| Agent 运行体与执行模式 | 面试官由同一运行体承载，共用单轮循环、工具调用与执行模式约束 |
| 会话内待确认改动与审批 | 面试中由模型提议的「生成练习计划」等写操作共用待确认与审批语义 |
| 不可变版本与快照 | 面试上下文以版本快照冻结，保证报告可复现 |
| 幂等与乐观锁 | 作答提交、评分生成共用同一套幂等键与冲突处理约定 |
| 离线模型目录 | 模型清单与上下文窗口字段取自仓库内的离线目录快照 |

### S2C.5 关键工程约束与冻结状态

1. 量表版本化：已冻结。评分维度的定义与锚点随报告存储，实现见 `backend/app/modules/interview/models.py` 的 `rubric_version` 字段。
2. 证据最小粒度：已冻结。只接受逐字出自作答原文的证据，见 `backend/app/modules/interview/service.py` 的逐字证据校验。
3. 语音降级阈值：仍开放。仓库已有 ASR 请求与轮询超时常量，但没有转写置信度阈值与「判定链路不可用并降级」的显式规则，需在开发启动前冻结。
4. 知识库检索口径：已冻结，检索器为 BM25 词法检索。「依据不足」的判定条件与命中下限见 `backend/app/modules/kb/service.py`。
5. 评分一致性抽检：已冻结。人工复核的抽样比例与一致性判定口径见 `docs/evaluation/rubric-consistency-procedure.md`。

五项中已冻结 4 项，仅语音降级阈值仍开放。

## S2D 成本模型及可行性分析

**负责人：开发（队长复核）**

### S2D.1 成本构成

| 类别 | 项 | 口径 |
| --- | --- | --- |
| 一次性 | 开发人力 | 按角色投入人日估算，以迭代计划为准 |
| 一次性 | 题库与知识库建设 | 当前两个验证岗位四类题的编写、校对与知识条目整理 |
| 运行 | 模型调用 | 按输入与输出 token 量 × 单价核算 |
| 运行 | 语音转写与播报 | 按音频时长计费，仅语音场次产生 |
| 运行 | 服务器与存储 | 应用、数据库、缓存与音频文件存储 |
| 运行 | 人工复核 | 评分一致性抽检所需人力 |

模型成本按场次 token 量核算，口径见下。

### S2D.2 成本估算方法与样例

单场面试的模型成本按「场次输入 token × 输入单价 + 场次输出 token × 输出单价」计算。

本方案不给出编造的「实测单场成本」数字：单场 token 消耗需在联调时用真实会话统计后填入。可确定的是核算路径——token 量从会话记录统计，与所用模型单价相乘即得，可被第三方复核。

成本控制手段：题目与依据生成一次后缓存、供后续场次共用；检索结果按岗位分片降低注入长度；纯文本场次不产生语音成本；练习计划生成使用较小模型。

### S2D.3 可行性分析

**技术可行性**：所需能力均在本项目内实现——多模型接口与密钥托管、Agent 运行体、版本快照、幂等与审批、权限与审计均已可用并有测试覆盖。本次交付包含业务域模块与界面，基础设施无需替换。

**工程可行性**：仓库已具备迁移机制、分层约束与自动质量门禁，新增模块可按同一套结构落地，避免架构漂移。

**成本可行性**：单场成本随模型选择可调；纯文本场次零语音成本；练习与复测共用同一链路，边际成本低。

**合规与可信可行性**：密钥由后端加密托管、只写不回显；报告默认仅本人可见并记录访问审计；评估结论强制附证据、不可测量表维度显式标为不适用，降低误导风险。

### S2D.4 主要风险与应对

1. 评估可信度风险：模型评分可能不稳定。应对：量表版本冻结、评分一致性抽检、每个维度强制附证据、证据不足不给分。
2. 语音链路风险：转写或播报服务不可用。应对：降级为纯文字并保留上下文，纯文本场次不产出音频维度分数。
3. 成本失控风险：长会话 token 增长。应对：上下文压缩、按岗位分片检索、可选小模型、成本统计入会话记录。
4. 知识库质量风险：条目错误会传导到题目与评分。应对：条目留来源标识、支持人工校订、无依据时标注依据不足。
5. 进度风险：题库建设与功能开发并行。应对：按岗位分批交付，先交付单岗位完整闭环再扩第二岗位。

### S2D.5 落地路径

先在校内小范围试点，用真实面试场次收集 token 与评分数，回填成本模型与量表一致性数据；据试点结果决定扩容岗位与是否引入实时语音。

下一阶段：BM25 + 向量检索（RAG）+ rerank 重排——在现有词法检索（BM25）之上叠加向量召回与重排，提升同义与长尾召回；命中片段注入出题提示词并落成引用、未命中标注「依据不足」的边界保持不变。
