# 01 测试设计

## 一、三层测试

| 层级 | 目标 | 范围 | 运行命令 | 通过判据 | 本次实测 |
| --- | --- | --- | --- | --- | --- |
| 后端 pytest | 验证 FastAPI 模块的接口契约、权限、幂等、错误码与启动配置 | \`backend/tests/\`（52 个测试文件） | \`cd backend && TEST_DATABASE_URL=postgresql+psycopg://localhost:5432/resumate_test_evidence .venv/bin/python -m pytest -q\` | 0 failed；使用独立库 \`resumate_test_evidence\`；迁移与 seed 正常 | 583 passed / 19.91s（\`logs/backend.txt\`） |
| 运行体 pytest | 验证 \`agent-core\` 的单轮循环、工具调用、会话绑定与脱敏 | \`agent-core/tests/\`（13 个测试文件） | \`cd agent-core && uv run pytest -q\` | 0 failed | 130 passed / 0.23s（\`logs/agent-core.txt\`） |
| 前端 vitest（RTL） | 验证页面与组件的渲染、交互、状态机与错误出口 | \`ui/src/**/*.test.ts(x)\`（81 个测试文件） | \`cd ui && pnpm test\` | 0 failed；81 个文件全部通过 | 81 files / 649 tests passed / 19.32s（\`logs/ui.txt\`） |
| 前端 story 渲染测试 | 用 Storybook 故事当渲染用例，先确认视觉与交互再接后端 | \`ui/src/**/*.stories.tsx\`（45 个文件） | \`cd ui && pnpm test\`（story 渲染断言随 vitest 一起跑） | story 文件可渲染且关键断言通过 | 计入 81 个 vitest 文件集合 |

- 为什么分三层：后端管契约与数据一致性，运行体管进程间的状态机与安全脱敏，前端管用户可见行为；三层的失败面互不替代。
- 前端采用 Storybook 先行：页面先在组件层用 story 确认视觉与交互，再接真实后端；story 与 \`.test.tsx\` 共享同一套 RTL 断言。

## 二、负向断言策略

只断言「接口返回 4xx」不算证明诚实；凡是可能把敏感信息透到用户可见面的出口，都同时写负向断言：DOM / 响应体不得出现完整 key、\`Authorization\`、\`Traceback\`、上游原始 message。

真实例子（文件:行号）：

- \`backend/tests/test_speech_tts.py:99-101\`：\`assert "raw upstream secret" not in message\` / \`assert "InvalidApiKey" not in message\` / \`assert "sk-tts-contract" not in message\`
- \`backend/tests/test_jd_parse_text.py:144\`：\`assert "sk-test-secret-key" not in response.text\`
- \`backend/tests/test_interview_aggregation.py:539\`：\`assert "Traceback" not in response.json()["message"]\`
- \`backend/tests/test_startup_config.py:108\`：\`assert secret not in caplog.text\`（启动日志不打印凭据值）
- \`ui/src/components/run-panel.test.tsx:761-763\`：\`expect(text).not.toContain("sk-live-abcdef123456")\` / \`not.toContain("Authorization")\` / \`not.toContain("Traceback")\`
- \`ui/src/components/resume-chat-panel.stories.test.tsx:38-40\`：DOM 不得含 \`Authorization\`、\`Traceback\`，且不匹配 \`/sk-[A-Za-z0-9]/\`
- \`ui/src/components/agent-onboarding.test.tsx:113\`：\`expect(screen.queryByText(/sk-abcdef/)).not.toBeInTheDocument()\`

对照正向断言：同一用例里先断言用户应看到的文案（如「去更新 Key」「重试」），再用上面的负向断言证明没有把机器原文透出去。

## 三、测试与需求的对应方式

1. 每个缺陷或功能先登记 Issue（\`docs/issues/closed/<id>-*.md\`），Acceptance Criteria 逐条写成可断言的行为；实现与测试同提交落地，提交信息带 \`Issue: <id>\` 关联。
2. 03-缺陷复现与回归.md 把「Issue → 修复提交 → 守护它的测试用例」串成一条链；02-测试用例清单.md 是这条链的完整用例底表。
3. 页面级约束（i18n 键结构一致、无硬编码中文、表单契约、隐私红线、伪实现）由 \`quality-gates/gates/\` 下的门禁在提交前强制执行，见 05-质量门禁执行记录.md。
