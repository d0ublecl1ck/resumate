# 修复简历库复制用例在高负载下的偶发超时

## Background

`ui/src/components/resume-library.test.tsx` 的「复制按钮调用 POST /resumes/{id}/duplicate 并进入副本」用例先 `render(<App/>)` 再 `await screen.findAllByRole("button", { name: "复制" })`。这条等待实际覆盖一整套异步挂载链路：`RequireAuth` 先解析当前用户，通过后才挂载 `ResumesPage`，后者并发发出 active / archived / templates / jds 四个 React Query 请求，四个都 resolve 之后才渲染出含「复制」按钮的卡片。

`findAllByRole` 走 Testing Library 默认的 1s 异步超时（`asyncUtilTimeout`）。CPU 被抢占时，这条 1 次鉴权 + 4 次查询 + 挂载渲染的链路耗时超过 1s，断言在页面仍停留在 `PageLoading` 时报 `Unable to find role="button" and name "复制"`（Red 证据见 Verification）。失败时抓到的 DOM 只剩 AppShell 与加载态，没有列表卡片，说明这是等待时长不足，不是组件状态竞态。

## Scope

- 只改测试文件 `ui/src/components/resume-library.test.tsx`：为该文件里所有依赖异步挂载结果的 `findBy*` / `waitFor` 等待给出显式、覆盖最坏情况的时间预算，保留 role/name 语义查询与断言本身。
- 为承载整个 App 挂载的用例显式提高 vitest 单测超时，使等待预算不被框架默认 5s 提前截断。

## Non-goals

- 不改 `ui/src/components/resume-library.tsx`、`ui/src/pages/resumes.tsx`、`ui/src/components/require-auth.tsx` 或路由/查询结构；本 issue 已判定根因不是组件竞态。
- 不改全局 Testing Library 配置（`ui/src/test-setup.ts`）或其它测试文件。

## Acceptance Criteria

- [x] `ui/src/components/resume-library.test.tsx` 中所有等待异步挂载结果的 `findBy*` / `waitFor` 都使用显式 timeout。
- [x] 在 CPU 高负载下连续运行该文件 10 次全绿，并给出汇总输出。
- [x] `pnpm -C ui test`、`pnpm -C ui build`、`archkit inspect .` 全部通过。
- [x] `.freak` 中该 flake 线索更新为已修并写明修法。

## Implementation

只在 `ui/src/components/resume-library.test.tsx` 引入两个模块级预算常量，并把该文件里所有等待异步挂载结果的调用改成显式预算：

- `APP_MOUNT_TIMEOUT_MS = 10_000`：作为每个 `findBy*` 的第三个参数与每个 `waitFor` 的 `{ timeout }`，替代 Testing Library 默认 1s `asyncUtilTimeout`。
- `APP_MOUNT_TEST_TIMEOUT_MS = 30_000`：作为四个 `it(...)` 的第三个参数，确保宽松的等待预算不会被 vitest 默认 5s 单测超时提前截断。

查询本身仍是 role/name 语义查询，断言与交互步骤未变；未改组件、路由、React Query 与全局 Testing Library 配置。

为什么这是正解而不是掩盖竞态：失败断言发生在点击之前，失败瞬间抓到的 DOM 只有 AppShell 与页面加载态、没有任何列表卡片，说明页面只是尚未完成「鉴权 + 4 个查询」的异步挂载，不存在「复制成功后重渲染导致断言时机不稳」的状态竞态。修复前无负载时首个用例已耗时 618ms，相对默认 1s 预算只有约 1.6x 余量，这是典型的等待预算不足。
