# 容量评估与全链路压测

## 容量估算方法

> 本文是 resumate 项目自建的种子知识语料（model-authored seed corpus），用于 A11 岗位题库的检索引用，非对任何外部规范、标准或出版物的摘抄。

先量化业务目标：日活、峰值 QPS、读写比、平均与 P99 响应时间。核心公式来自利特尔法则：并发数 = QPS × 平均 RT，据此把业务 QPS 换算成需要的并发线程与实例数。单机容量靠基准压测得到：逐步加压直到 CPU、内存、连接池、线程池队列或下游 RT 出现拐点，记录该点的 QPS 作为单机水位，再留 30% 到 50% 余量。注意瓶颈往往不在应用本身，而在数据库连接数、Redis 带宽、MQ 分区数、带宽或下游第三方接口的配额。

## 全链路压测

单接口压测会低估真实压力，全链路压测要覆盖网关、服务、缓存、数据库、消息与下游。关键是流量染色与数据隔离：压测请求带专属标记，中间件按标记路由到影子库、影子表或独立集群，避免污染生产数据、影响真实用户。压测目标要覆盖峰值场景（大促零点）和异常场景（缓存失效、主从延迟、下游超时）。压测前评估风险并通知相关方，压测中盯紧生产指标防止误伤，压测后输出瓶颈清单与扩容方案。

## 水位与扩容策略

容量不是一次性结论，要持续监控水位：CPU、内存、GC 频率、数据库 QPS 与慢查询、连接数、线程池队列深度、缓存命中率、MQ 积压。扩容优先无状态服务水平扩展，数据库分片或加只读副本。扩容能力要提前验证，别在故障时才发现镜像拉不下来或配置不一致。限流阈值与容量水位挂钩，扩缩容后同步调整限流规则，并保留一键降级预案。

## 预案与演练

容量方案必须配可执行的预案：明确触发指标、责任人、执行动作、预期效果和回切条件。定期做故障演练（缓存宕机、数据库主从切换、下游熔断），验证预案真的能执行、监控真的能看到、告警真的能触达，而不是只写在文档里。
