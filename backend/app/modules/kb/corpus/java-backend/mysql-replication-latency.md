# MySQL 主从复制与延迟

## 复制原理

> 本文是 resumate 项目自建的种子知识语料（model-authored seed corpus），用于 A11 岗位题库的检索引用，非对任何外部规范、标准或出版物的摘抄。

MySQL 复制基于 binlog：主库把变更写成 binlog，从库的 IO 线程拉取并写入 relay log，SQL 线程（或并行 worker）回放 relay log 应用到从库。binlog 格式有 STATEMENT（记录 SQL，函数、时间戳等可能不一致）、ROW（记录行变更，数据安全但日志量大，主流选择）、MIXED。复制模式有异步、半同步（至少一个从库收到并写入 relay log 才返回，兼顾安全与性能）、组复制（基于 Paxos 的多主一致性）。GTID 用全局事务 ID 替代文件名加偏移量，主从切换与故障恢复更简单。

## 延迟成因与判断

Seconds_Behind_Master 并不完全可靠：从库 IO 线程断了它会显示 NULL，大事务执行途中也可能长期显示 0，应该结合 GTID 差值与实际业务对账判断。延迟常见原因：主库有大事务（一次删几百万行、大批量导入），从库只能整个事务回放；从库单线程回放慢，需要开并行复制（binlog_group_commit_sync_delay、slave_parallel_workers、按组提交并行）；从库承担大量读或备份导致资源竞争；网络带宽不足或跨机房。DDL 在从库串行执行也会造成长延迟。

## 读写分离下的一致性

读写分离后，写主库、读从库，用户刚写完立刻读可能读不到，这是业务必须处理的一致性窗口。手段有：写后短时间强制走主库（按用户或会话标记）、关键读带上 GTID 等待从库追上（wait_for_executed_gtid_set）、用半同步降低延迟概率、或对强一致读直接走主库。这些策略会牺牲部分读扩展能力，要按业务重要性分级，而不是全部强制走主。

## 监控与容量

要监控复制状态（IO/SQL 线程是否 running）、GTID 差值、relay log 堆积、从库磁盘与延迟趋势，并对延迟设告警。主从切换要有演练：明确切换判定、数据补偿、应用重连与缓存清理步骤。从库数量不是越多越好，每个从库都增加主库的 binlog 发送与网络负担，要按读流量与容灾等级规划。
