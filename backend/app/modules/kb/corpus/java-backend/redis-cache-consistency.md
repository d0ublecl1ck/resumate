# Redis 缓存一致性与穿透击穿雪崩

## 缓存与数据库一致性

最常用的是 Cache Aside：读时先查缓存，未命中查库并回填；写时先更新数据库，再删除缓存，而不是更新缓存。删除缓存能减少并发写导致的脏数据，但删除失败或主从复制延迟仍会留下旧值，于是有延迟双删：更新库后删一次缓存，延迟几百毫秒再删一次，覆盖读请求回填旧值的时间窗。更彻底的做法是订阅数据库 binlog（如 canal）异步删缓存，把一致性收敛到消息链路，保证最终一致。要明确业务能接受的是最终一致而非强一致，缓存和数据厍之间永远存在时间窗。

## 穿透、击穿与雪崩

穿透指查一个数据库里也不存在的 key，请求每次都打到库上。解法是缓存空值（设短过期）或用布隆过滤器提前拦截，布隆过滤器有误判但不漏判，删除数据时难以回收，需要配合计数或定期重建。击穿指某个热点 key 过期瞬间大量并发压到库上，解法是互斥锁只放一个请求回源，或逻辑过期（value 里带过期时间，后台异步刷新，读取方永远拿到旧值而不是等待）。雪崩指大批 key 同时过期或缓存集群宕机，解法是过期时间加随机抖动、多级缓存（本地 Caffeine 加 Redis）、缓存宕机时用熔断限流保护数据库、以及热点数据预热。

## 持久化与容量治理

RDB 是快照，恢复快但可能丢较多数据；AOF 记录写命令，appendfsync=everysec 表示每秒刷盘，最坏丢约一秒的写入，always 最安全但性能差，no 交给操作系统。AOF 重写（BGREWRITEAOF）在后台 fork 子进程压缩命令，重写期间新写入进入重写缓冲区，完成后追加到新文件，主进程不阻塞。混合持久化把 RDB 全量与增量 AOF 结合，兼顾恢复速度和数据安全。线上还要治理大 key 和热 key：大 key 会阻塞单线程、拖慢主从同步，热 key 会打满单个分片，解法是拆分、本地缓存、读写分离或增加副本。

## 缓存使用纪律

Redis 是单线程处理命令（6.0 后网络 IO 多线程），一条慢命令会阻塞所有请求，禁止在生产执行 keys、flushall、大范围 zrange 等操作，用 scan 渐进遍历。分布式锁要考虑锁续期、误删（value 存唯一标识、Lua 校验后删）、以及主从切换导致的锁丢失问题，强一致场景应评估 Redlock 的争议或改用 ZooKeeper、etcd。
