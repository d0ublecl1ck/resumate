# 分布式事务与幂等

## 分布式事务的取舍

> 本文是 resumate 项目自建的种子知识语料（model-authored seed corpus），用于 A11 岗位题库的检索引用，非对任何外部规范、标准或出版物的摘抄。

跨库跨服务的强一致很难兼顾性能与可用性，BASE 思路是基本可用、软状态、最终一致。两阶段提交（2PC）有同步阻塞、协调者单点、数据不一致窗口的问题，XA 是它在数据库层的标准实现，适合银行内部低并发场景，互联网业务很少直接用。Seata 提供 AT（自动补偿反向 SQL）、TCC（Try-Confirm-Cancel 三段式，业务侵入大但可控）、Saga（长事务编排，每步有补偿）等模式。更轻量的是本地消息表和事务消息：业务与写消息表在同一个本地事务里提交，再由定时任务投递消息，下游消费成功才标记完成；RocketMQ 的事务消息把这一过程内置，先发半消息，本地事务成功再提交，失败则回滚。

## 幂等是最终一致的前提

任何自动重试、消息重投、补偿重放的链路都要求操作幂等，否则一致性会退化成重复扣款或多发权益。幂等实现：数据库唯一索引兜底最简单可靠；状态机只允许从合法前态推进到目标态，重复请求直接返回上次结果；去重表按业务流水号记录处理状态；Redis setnx 或 token 做防重提交；金额计算用「设置为某值」而不是「增加某值」。要注意幂等键的来源和有效期，以及并发下唯一索引冲突的异常处理。

## 分布式锁与热点扣减

分布式锁常用 Redis（SET NX PX 加唯一 value，Lua 校验后释放）或 ZooKeeper 临时顺序节点。Redis 主从异步复制下，主节点宕机可能丢失锁，Redlock 试图解决但存在时钟与网络分区的争议，强一致场景应评估 ZooKeeper 或数据库唯一约束。热点账户或秒杀库存扣减，单一热点行会成为瓶颈，可用分段扣减（把库存拆成 N 段分别扣，失败再换段）、Redis 预扣减加异步落库、消息队列串行化，并在数据库层用条件更新（UPDATE ... WHERE stock >= n）保证不超卖。

## 对账与补偿

最终一致需要可观测的补偿：定时对账比对上下游流水，找出差异后按幂等方式补正，差异超过阈值就告警并人工介入。补偿要有重试上限、退避、死信与人工处理入口，不能让失败任务静静消失。
