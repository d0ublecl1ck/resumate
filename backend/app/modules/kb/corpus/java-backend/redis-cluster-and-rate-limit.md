# Redis 集群模式与大促限流治理

## 集群模式与分片路由

> 本文是 resumate 项目自建的种子知识语料（model-authored seed corpus），用于 A11 岗位题库的检索引用，非对任何外部规范、标准或出版物的摘抄。

Redis Cluster 把键空间分成 16384 个槽，按 CRC16(key) mod 16384 决定归属节点，客户端缓存槽映射直接连目标节点，MOVED 与 ASK 用于重定向和迁移。多键命令和事务要求所有 key 在同一槽，跨槽要用 hash tag 把相同业务前缀放进同一槽。集群模式下单分片仍然只有一个主线程，热点 key 会把某个分片的 CPU 打满，而其他分片空闲——大促的限流计数器如果按接口维度构造 key，热门接口会把对应分片顶满。治理手段是拆分热点计数（把全局阈值拆成 N 个子计数器）、读写分离、加副本，或对极热 key 改用本地限流。

## Lua 滑动窗口的实现与成本

滑动窗口限流器常用 ZSET 存请求时间戳，Lua 脚本里先 ZREMRANGEBYSCORE 清理过期成员，再 ZCARD 判断是否超限，最后 ZADD 记录本次请求，整套读写在一个原子脚本里完成。成本在于：脚本越长、操作的元素越多，单线程阻塞越久；ZSET 成员随时间累积，内存与清理成本随 QPS 上升；同一 key 的所有请求都落到同一分片，热门接口天然形成单分片热点。优化方向是把窗口长度和 QPS 阈值算准，控制 ZSET 规模；能用固定窗口计数器的场景不要上 ZSET；脚本用 EVALSHA 复用，避免每次传脚本正文；必要时把限流状态按时间片预聚合，减少每次请求的操作数。

## CPU 打满的治理

Redis 集群 CPU 打满通常不是集群整体，而是某个分片或某个节点的单线程跑满。先看 INFO、SLOWLOG 与监控定位是慢命令、大 key、脚本阻塞还是单纯 QPS 太高。限流器本身成为瓶颈时，要把「精确计数」降级为「近似计数」：用滑动窗口的粗粒度时间片、用令牌桶替代 ZSET、把多级阈值合并成一次 INCR。还要避免在限流脚本里做 KEYS、SMEMBERS 这类 O(N) 操作，单个脚本的耗时上限要压到毫秒级。扩容分片、把限流 key 打散到多个槽、给脚本加限流（例如同一接口每 N 毫秒才写一次 Redis），都能把单分片压力摊开。

## 分层限流与本地兜底

大促限流要分三层：客户端或网关做单机本地限流（令牌桶、Guava RateLimiter），实例内先削峰；Redis 集群做全局阈值，用滑动窗口或令牌桶保证总量；服务内部再用 Sentinel 做细粒度保护。本地限流要留出与全局阈值的比例关系，例如全局阈值按实例数均分再留 10% 抖动，否则某台实例故障后其他实例会超发。Redis 故障或延迟升高时必须能快速降级：要么直接失败保护后端，要么按本地阈值放行并告警，绝不能无限阻塞在 Redis 调用上。限流 key 要带版本和过期时间，避免大促后残留计数影响下一个活动。
