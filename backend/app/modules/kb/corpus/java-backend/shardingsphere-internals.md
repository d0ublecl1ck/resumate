# ShardingSphere 分片内核

## SQL 解析与分片路由

> 本文是 resumate 项目自建的种子知识语料（model-authored seed corpus），用于 A11 岗位题库的检索引用，非对任何外部规范、标准或出版物的摘抄。

ShardingSphere 有 JDBC 与 Proxy 两种形态：前者以数据源代理方式嵌入应用，后者作为独立数据库代理。一次查询的内核流程固定为五步——SQL 解析、路由、改写、执行、归并。解析阶段用方言解析器把 SQL 变成 AST，识别分片键、表名与分页信息；路由阶段由 RouteEngine 根据分片规则计算目标库表。

路由分三类：标准路由覆盖「分片键 = 单值」或「分片键 IN」，每个值精确定位到一个分片；笛卡尔路由出现在没有分片键条件、或 join 的表之间没有绑定关系时，会产生分片组合，性能最差；全库表路由即不带分片键的查询，必须广播到所有分片再由中间件归并，分片越多越慢，线上应禁止。

## 绑定表、广播表与改写归并

绑定表（Binding Table）指分片规则完全一致的主子表，例如订单表与订单明细表都按 order_id 分片。声明绑定关系后，join 只在同一分片内进行，不会退化成笛卡尔积，是分片下保住联表查询的关键配置。广播表（Broadcast Table）指每个分片都保存全量数据的小字典表，join 无需跨库，代价是写入要广播到所有分片、一致性与性能都要额外评估。

改写阶段把逻辑表名替换为真实物理表名，并针对分页、聚合、自增主键补列做二次改写：深分页 LIMIT 1000000, 20 会被改写成对每个分片下发 LIMIT 0, 1000020，这是 OOM 的直接原因。归并阶段分流式归并与内存归并，排序、聚合、分页、去重都在这里完成，DISTINCT 与 GROUP BY 大结果集在内存归并下同样有 OOM 风险，应尽量带上分片键或迁移到 ES、数仓。

## 分布式主键与执行引擎

分片后不能再用单库自增，ShardingSphere 内置 Snowflake、UUID 以及基于号段的分布式主键生成器。Snowflake 由时间戳、workerId 与序列号组成，必须处理时钟回拨；号段模式一次申请一批 ID 缓存在本地，减少数据库往返，但重启会浪费一段号段。执行引擎按路由结果并发执行多个分片查询，线程池与连接数要按「分片数 × 并发」评估，避免打爆数据库连接。

分布式主键、绑定表、广播表三者要在建表阶段一次性设计好，后期补配会造成大量数据迁移；任何改写都要求分片键出现在查询条件里，否则只能广播。
