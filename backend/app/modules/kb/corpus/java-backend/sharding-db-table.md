# MySQL 分库分表与分片键

## 何时分库分表

> 本文是 resumate 项目自建的种子知识语料（model-authored seed corpus），用于 A11 岗位题库的检索引用，非对任何外部规范、标准或出版物的摘抄。

分库分表是最后手段，不是默认方案。单表行数到千万级、写入或查询出现明显瓶颈时才考虑，而且要先排除更便宜的优化：补索引、去掉 SELECT *、归档冷数据、读写分离、加缓存、优化 SQL 与连接池。经验阈值是单表 2000 万行或单表数据量超过几十 GB 时评估分片。分表的收益来自把单点压力摊到多个物理库表，代价是跨片查询、分布式事务、扩容迁移和运维复杂度全面上升。

## 分片键选择

分片键要满足三个条件：查询命中率最高、数据分布均匀、尽量少跨片。订单场景里 C 端按 user_id 查、商家按 merchant_id 查、客服按 order_id 查，三者天然冲突，只能选一个主分片键，其余用「基因法」把次要键的片段冗余进主键，或建异构索引表（用 canal 订阅 binlog 写一份按 merchant_id 分片的查询表）。取模分片简单但扩容要全量迁移；一致性哈希、Range、预分片（一开始就分够 1024 片，物理上先合并）能缓解扩容；双倍扩容加双写迁移是常见落地路径。

## 深分页与非分片键查询

不带分片键的查询会广播到所有分片再归并，分片越多越慢，必须禁止。深分页（LIMIT 10000,20）在中间件里要对每个分片取 offset+limit 条再内存归并排序，代价随页码线性上升；解决办法是改成基于游标（上一页最后一条的 id 或时间）的连续翻页、把大偏移查询迁到 ES 或数仓、或用二次查询先在各分片取最小有序值再回表。这类需求要和产品明确分页能力上限，而不是硬扛。

## 分布式主键与索引

分片后不能再用单库自增主键，要用雪花算法（时间戳+机器号+序列）或号段模式（数据库批量发号，缓存到本地）。分片表上的唯一约束必须包含分片键，否则只能靠全局校验。分片后每张物理表仍要按本表查询模式建索引，分片键通常就是主键或与主键组合，普通二级索引要评估回表代价。跨片 JOIN、跨片聚合、跨片事务能避免就避免，避免不了就在应用层聚合或引入中间件支持。
