# 前端工程化与 CI

## 仓库与规范

> 本文是 resumate 项目自建的种子知识语料（model-authored seed corpus），用于 A11 岗位题库的检索引用，非对任何外部规范、标准或出版物的摘抄。

多包项目用 monorepo 管理（pnpm workspace），统一依赖版本与构建脚本，避免各仓库重复造轮子。代码规范由 ESLint 加 Prettier 承担，配合 TypeScript 严格模式；提交规范用 Conventional Commits 加 commitlint，通过 husky 与 lint-staged 在提交前只检查改动文件，兼顾速度与质量。环境变量与路径别名要统一约定并在各包共享，禁止每个项目各写一套，导致联调时行为不一致。依赖要定期升级并锁文件，安全漏洞用 audit 与 dependabot 跟进。

## CI 流水线

CI 至少包含：安装依赖（启用缓存）、类型检查、Lint、单测、构建，任何一步失败就阻断合并。PR 阶段并行跑这些任务以缩短反馈，构建产物用于预览部署，评审者点开真实链接就能验收。主分支合并后触发生产构建与发布，产物带内容哈希、上传 CDN、执行冒烟测试。构建缓存、并行与增量是提速重点，但要防止缓存导致产物陈旧，需要按 lockfile 与源码哈希做正确失效。

## 构建工具与迁移

webpack 生态成熟、插件丰富；Vite 基于 esbuild 预构建与 Rollup 生产构建，开发启动快；rsbuild、Rspack 走 Rust 提效路线。工具迁移要先统一基础配置与插件，再逐包灰度，保证产物对比通过。tsconfig 从宽松到 strict 的迁移要分阶段：先补类型声明与 noImplicitAny，再开 strictNullChecks，配合 ESLint 禁止显式 any，把历史问题登记为待办而不是一次性压给业务。

## 质量门禁

把可执行的规则做成质量门禁：禁止硬编码文案、禁止裸色值、页面必须有测试、i18n 键结构一致等，由统一 runner 在本地钩子与 CI 同时跑，规则和豁免都进仓库可评审。门禁要能给出「文件:行号加正确做法」，而不是一句失败；豁免必须写明原因，不能用来掩盖真实问题。工程化的目标是把团队共识变成自动可执行的检查，减少靠人盯。
