# 微前端架构

## 方案选型

> 本文是 resumate 项目自建的种子知识语料（model-authored seed corpus），用于 A11 岗位题库的检索引用，非对任何外部规范、标准或出版物的摘抄。

微前端解决的是多个团队、多个技术栈、独立构建部署的应用如何组合成一个页面。常见方案：iframe 隔离最彻底但路由、弹窗、通信、性能都受限；single-spa 提供应用生命周期与路由编排，是多数框架的基础；qiankun 在其上做了沙箱、样式隔离与资源加载；Module Federation 让构建期或运行期共享模块与依赖，适合同构建体系的团队；Web Components 加 Shadow DOM 提供原生隔离。选型核心是隔离强度、共享依赖、通信成本和团队技术栈，不要为了微前端而微前端，单体应用够用就不拆。

## 沙箱与隔离

JS 沙箱常用 Proxy 拦截 window 的读写，或快照 window 在子应用卸载后恢复，防止子应用污染全局。CSS 隔离可用 Shadow DOM（隔离强但样式穿透与主题麻烦）、scoped 前缀加构建期改写、或运行期动态增删样式表。要处理全局变量、定时器、事件监听的清理，子应用卸载时调用 unmount 释放资源，否则反复切换会内存泄漏。

## 接入与首屏

主应用与子应用通过路由分发、全局状态或事件总线通信，接口要定义清晰，避免子应用直接改主应用内部状态。接入后首屏退化通常有几个原因：子应用资源串行加载、重复引入同一框架导致体积膨胀、子应用初始化在主线程做重活、样式注入引发重排。优化手段：预加载子应用资源、共享公共依赖、子应用按需初始化、主应用先渲染骨架。加载失败要有降级到错误页或旧版本的能力。

## 治理与成本

微前端带来构建、依赖、版本、监控、发布流程的复杂度，必须配套统一规范：公共依赖版本对齐、路由与鉴权约定、埋点与错误上报口径一致、发布与回滚流程可独立。没有治理能力时，微前端会把单体的耦合换成分布式耦合，问题更难定位。引入前要评估团队规模与交付节奏是否真的需要独立部署。
